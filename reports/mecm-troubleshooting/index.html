When MECM deployments don't reach every PC

Two problems stop patching at less than 100%: devices that show as inactive, and software that fails to update. Fix both by grouping failures by cause, not by device.

01Inactive devices

A deployment isn't lost when a device is inactive. Once the PC comes back online and checks in, it picks up the deployment and installs it, as long as the deployment hasn't expired. Set deadlines but no expiry date, and late devices catch up on their own.

Then sort the inactive devices into these groups:

CauseHow to tellFix
PC is switched off or rarely usedLast logon is old in AD tooWake-on-LAN, or a power policy that keeps PCs on overnight on patch days. If a PC is never used, remove it.
Laptop off the office network (home, no VPN)Comes back to active when the user visits the officeA Cloud Management Gateway (CMG) so clients reach MECM over the internet, or co-management with Intune
Broken MECM clientPC responds to ping but has no MECM heartbeatRepair or reinstall the client (see below)
Stale record (reimaged, renamed or scrapped)Duplicate names, or the device no longer existsDelete the old record. Turn on the Delete Inactive Client Discovery Data and Delete Aged Discovery Data maintenance tasks.
Boundary problemClient is active but can't download contentPut the PC's subnet or IP range in a boundary group that has a distribution point

Repair broken clients at scale

  • Use a GPO startup script that checks the CcmExec service on every boot and reinstalls the client if it's broken. The free community ConfigMgr Client Health script by Anders Rødland does this and is widely used.
  • Or use Client Push on the device collection with Always install, even if already installed.
  • Track the problem with a collection called Clients - Inactive, and check it weekly:
Monitoring → Client Status

02Software that fails to update

Open the Error tab of the deployment. It groups failed PCs by error code. Fix each code once, and it fixes every PC with that code.

Monitoring → Deployments → [deployment] → Error tab
Error / symptomUsual causeFix
1618 / 1603App is open (Chrome, Teams, Java, Adobe), or another install is runningWrap the install in PSADT (PowerShell App Deployment Toolkit). It closes the app or asks the user to, then installs. Or deploy outside working hours.
Install says success, scanner still flags itPer-user install in the user's profile (Chrome, Zoom, Teams). MECM runs as SYSTEM and can't see it.Uninstall the per-user copies with a script, then deploy the machine-wide version
0x87D00324Wrong detection method: app not detected after installDetect the new version by file version or MSI product code, not just "file exists"
Old version stays installedSupersedence uninstall fails because the vendor's uninstall command is differentAdd a custom uninstall script, or clean up with Run Scripts
0x87D00607Content isn't on the distribution point, or a boundary problemDistribute content to all DPs and check boundary groups
3010Needs a restart. This is not an error.Set a restart deadline in client settings
0x8024xxxxWindows Update: pending restart, low disk space, or broken update componentsRestart, free disk space, run DISM /Online /Cleanup-Image /RestoreHealth through Run Scripts

The biggest wins are usually PSADT, for apps that are open during install, and cleaning up per-user installs.

03Client log files

To see the real reason on a failing PC, open these files in C:\Windows\CCM\Logs:

AppEnforce.logInstall command and exit code
AppDiscovery.logDetection results
ContentTransferManager.log · CAS.logDownload problems
WUAHandler.log · UpdatesDeployment.logWindows Update problems

04Weekly routine

  1. 1
    Check Clients - Inactive. Repair, wake up or delete those devices.
  2. 2
    Open the Error tab on each deployment and fix the top 2–3 error codes.
  3. 3
    Anything still failing after 2 attempts: reimage the PC, or log it as an exception with an owner and a review date.
Prepared October 2026. Error codes and menu names come from general MECM knowledge and can differ slightly between versions. Confirm them against your console and logs.
