When MECM deployments don't reach every PC

A hands-on guide to the two problems that stop patching short of 100%: devices that show as inactive, and software that fails to install. Every fix includes the exact steps and a check that proves it worked.

00Tools you need

  • MECM console, with rights to create collections, scripts and deployments.
  • CMTrace, the MECM log viewer. It highlights errors in red. Every MECM client has it at C:\Windows\CCM\CMTrace.exe. Copy it to your admin PC.
  • Windows PowerShell 5.1 on your admin PC, run as an account that is a local admin on the PCs. The scripts below use commands that only work in 5.1, not PowerShell 7.
  • Active Directory module for PowerShell, from RSAT, for the Get-ADComputer command.
  • Access to \\<PC>\c$ on the PCs, so you can read their logs remotely.

Read a PC's log without walking to it: open CMTrace → File → Open → type \\<PC-NAME>\c$\Windows\CCM\Logs\AppEnforce.log.

01Find every inactive PC in one list

Create a collection that always contains the PCs MECM marks as inactive, so you never have to search for them.

  1. Go to Assets and Compliance → Device Collections → Create Device Collection.
  2. Name: Clients - Inactive. Limiting collection: All Systems. Click Next.
  3. Add Rule → Query Rule. Name it Inactive → Edit Query Statement → Show Query Language → paste the query below → OK.
  4. Tick Schedule a full update on this collection → set it to daily → Finish.
WQL · devices whose MECM client is inactive
select SMS_R_System.ResourceID, SMS_R_System.Name
from SMS_R_System
inner join SMS_G_System_CH_ClientSummary
  on SMS_G_System_CH_ClientSummary.ResourceId = SMS_R_System.ResourceId
where SMS_G_System_CH_ClientSummary.ClientActiveStatus = 0

Create a second collection, Clients - Missing, the same way for PCs that have no MECM client at all:

WQL · devices with no MECM client
select SMS_R_System.ResourceID, SMS_R_System.Name
from SMS_R_System
where SMS_R_System.Client is null or SMS_R_System.Client = 0

Then add useful columns. Open the collection, right-click the column header, and tick Client Activity, Client Check Result and Last Policy Request.

✓ Check it worked

The collection shows a member count. Click it and you see the PC names, with Client Activity = Inactive. Write down the number; it's your starting point. Copy the names into Notepad: select all rows → Ctrl+C → paste. Save them as C:\Temp\inactive.txt, one name per line.

02Sort inactive PCs by cause, automatically

Run this from your admin PC. It checks every PC in the list: does it answer on the network, when did it last log on to the domain, and is the MECM client service running?

PowerShell 5.1 · triage inactive PCs
Import-Module ActiveDirectory
$pcs = Get-Content C:\Temp\inactive.txt | Where-Object { $_.Trim() }

$result = foreach ($pc in $pcs) {
    $pc = $pc.Trim()
    $ad = Get-ADComputer $pc -Properties LastLogonDate, Enabled -ErrorAction SilentlyContinue
    $online = Test-Connection $pc -Count 1 -Quiet
    $svc = 'Offline'
    if ($online) {
        try   { $svc = (Get-Service -ComputerName $pc -Name CcmExec -ErrorAction Stop).Status }
        catch { $svc = 'NotFound/NoAccess' }
    }
    [pscustomobject]@{
        Name        = $pc
        InAD        = [bool]$ad
        ADEnabled   = $ad.Enabled
        LastLogonAD = $ad.LastLogonDate
        Online      = $online
        CcmExec     = $svc
    }
}

$result | Sort-Object Online, LastLogonAD | Format-Table -AutoSize
$result | Export-Csv C:\Temp\inactive-triage.csv -NoTypeInformation

If your firewall blocks ping, Online shows False for PCs that are actually on. In that case, test with Test-NetConnection <PC> -Port 445 instead.

Open C:\Temp\inactive-triage.csv in Excel and match each row to a cause:

What the row showsCauseGo to
InAD = False, or ADEnabled = False, or LastLogonAD older than 90 daysStale record: PC scrapped, renamed or reimagedFix A
Online = False, LastLogonAD recentPC is off, or a laptop away from the officeFix B
Online = True, CcmExec = NotFound/NoAccess or StoppedMECM client broken or missingFix C
Online = True, CcmExec = RunningClient runs but can't reach the management pointFix D

03Fix each cause

FIX AStale records (PC no longer exists)

Do this
  1. Confirm with the asset list or the user that the PC is really gone. If it is, delete it in AD.
  2. In MECM, select the device in Clients - Inactive → right-click → Delete.
  3. Stop it happening again. Go to Administration → Site Configuration → Sites → select your site → Site Maintenance (ribbon). Enable Delete Inactive Client Discovery Data (for example 90 days) and check that Delete Aged Discovery Data is enabled.
  4. Go to Administration → Hierarchy Configuration → Discovery Methods → Active Directory System Discovery → Properties → Options. Tick Only discover computers that have logged on to a domain in a given period of time and set it to 90 days. This stops old AD accounts from creating devices again.
✓ Check it worked

After the next collection update, the member count of Clients - Inactive drops by the number of devices you deleted. They don't come back after the next discovery cycle.

FIX BPC is switched off, or the laptop is off-network

Do this
  1. Office PCs that are switched off: use Wake-on-LAN.

    Turn on Wake-on-LAN in the PC's BIOS. Most vendors (Dell, HP, Lenovo) can also do this with their own tools.

    Go to Administration → Client Settings → [your settings] → Power Management → set Allow network wake-up = Enable.

    To wake a PC: right-click the device or collection → Client Notification → Wake Up. This needs at least one other MECM client that is switched on in the same subnet.

  2. Deployments wait for the PC. In every deployment, set a deadline and leave expiry empty. When the PC comes back, it installs automatically.
  3. Laptops that are never in the office: ask users to connect to VPN once a week as a short-term fix. The long-term fix is a Cloud Management Gateway (CMG), which lets clients reach MECM over the internet. It needs an Azure subscription and a certificate, so plan it as a separate project.
✓ Check it worked

Send Wake Up to one test PC. Within a few minutes it answers Test-Connection <PC>. Within an hour or so, its Last Policy Request time updates in the console. Client Activity changes to Active at the next client activity evaluation, which can take up to a day.

FIX CMECM client broken or missing

Option 1: reinstall from the console (many PCs at once)
  1. Select the PCs (or a whole collection) → right-click → Install Client.
  2. Tick Always install the client software and Uninstall existing Configuration Manager client before the client is installed. Choose your site → Finish.
  3. This uses your Client Push account. That account must be a local admin on the PCs, and the PC firewall must allow File and Printer Sharing and WMI.
Option 2: reinstall on one PC by hand (when push fails)

Run on the PC as admin:

cmd · remove and reinstall the client
C:\Windows\ccmsetup\ccmsetup.exe /uninstall
:: wait until ccmsetup.exe disappears from Task Manager, then:
\\<SITE-SERVER>\SMS_<SITECODE>\Client\ccmsetup.exe /mp:<MP-FQDN> SMSSITECODE=<SITECODE>

If the reinstall fails with WMI errors, first run winmgmt /verifyrepository. If it reports the repository is inconsistent, run winmgmt /salvagerepository and reinstall again.

Option 3: repair automatically on every boot

Use the free community ConfigMgr Client Health script by Anders Rødland. Put it on a file share, edit its config.xml with your site code and client share, and run it with a GPO computer startup script or a scheduled task. It checks the client, WMI and services, and reinstalls when needed. Follow its own README for setup.

✓ Check it worked
  • On the PC, C:\Windows\ccmsetup\Logs\ccmsetup.log ends with CcmSetup is exiting with return code 0. For console push, the site server's ccm.log shows the push result for that PC.
  • On the PC, open Control Panel → Configuration Manager → Actions tab. A healthy client lists about 8–10 actions. If it shows only 2, it isn't receiving policy yet. Wait 15 minutes, or run the command below.
  • Run the PowerShell below on the PC. It should print your site code and management point.
PowerShell · confirm the client is assigned and pull policy now
Get-Service CcmExec
Get-CimInstance -Namespace root\ccm -ClassName SMS_Authority | Select-Object Name, CurrentManagementPoint
# Machine Policy Retrieval & Evaluation Cycle
Invoke-WmiMethod -Namespace root\ccm -Class SMS_Client -Name TriggerSchedule -ArgumentList '{00000000-0000-0000-0000-000000000021}'

In the console, Last Policy Request for that PC updates within the hour. The PC leaves Clients - Inactive after the next client activity evaluation.

FIX DClient runs but can't reach MECM (communication or boundaries)

Do this
  1. Open these logs on the PC with CMTrace and look for red lines:
    LogHealthyProblem looks like
    ClientIDManagerStartup.logClient is registeredRegistration pending / failed (certificate or duplicate ID)
    LocationServices.logLists your management point and siteNo MP found / no site assignment
    CcmMessaging.logSuccessful posts to the MPRepeated Post to http://… failed errors
  2. If the MP can't be reached, test from the PC: Test-NetConnection <MP-FQDN> -Port 80 (use 443 for HTTPS). If it fails, the problem is the firewall, VPN or DNS, not MECM.
  3. If logs mention boundaries or no content location, check the PC's IP. Go to Administration → Hierarchy Configuration → Boundaries. Make sure the PC's subnet or IP range is in a boundary. In Boundary Groups, make sure that boundary is in a group that has a distribution point on its References tab.
  4. If the client shows a duplicate ID (common after cloning PCs without sysprep), reinstall the client with Fix C, Option 2.
✓ Check it worked

CcmMessaging.log shows successful posts with no new errors. Run the policy command from Fix C, and Last Policy Request updates in the console.

04Find failed installs and their real error

  1. Go to Monitoring → Deployments → select the deployment → View Status (bottom pane).
  2. Click the Error tab. Failures are grouped by error code. Expand a code to see the PCs. Fix the code with the most PCs first.
  3. Pick one PC from that group and open its log remotely in CMTrace:

    Applications: \\<PC>\c$\Windows\CCM\Logs\AppEnforce.log

    Windows updates: \\<PC>\c$\Windows\CCM\Logs\UpdatesDeployment.log and WUAHandler.log

  4. In AppEnforce.log, find these lines for your app:

    Executing Command line: "msiexec.exe" /i … shows exactly what MECM ran.

    Process 4321 terminated with exitcode: 1603 shows the installer's real result.

Then go to the matching fix below.

05Fix by error code

FIX E1618 / 1603 App is in use, or another install is running

1618 means another install was running. MECM retries this automatically, so it usually clears by itself. 1603 is a general failure; very often the app was open (Chrome, Teams, Java, Adobe), so files were locked.

Do this: a wrapper script that closes the app safely
  1. Put the MSI and the script below in the application's content folder. Name the script install.ps1.
  2. In the application, open Deployment Types → Properties → Programs. Set the install program to:

    powershell.exe -ExecutionPolicy Bypass -NoProfile -File install.ps1

  3. On the User Experience tab, set Installation behavior = Install for system, and Logon requirement = Whether or not a user is logged on.
  4. Right-click the application → Update Content, so the distribution points get the new script.
PowerShell · install.ps1 (Chrome example)
$process = 'chrome'
$msi     = Join-Path $PSScriptRoot 'googlechromestandaloneenterprise64.msi'
$log     = "$env:windir\Temp\chrome-install.log"

# If a user is logged on and the app is open, close it (they lose open tabs, so prefer out-of-hours deadlines)
Get-Process $process -ErrorAction SilentlyContinue | Stop-Process -Force
Start-Sleep -Seconds 3

$p = Start-Process msiexec.exe -ArgumentList "/i `"$msi`" /qn /norestart /l*v `"$log`"" -Wait -PassThru
exit $p.ExitCode

This closes the app without asking. For a friendlier version that warns users and gives a countdown, use PSADT (PowerShell App Deployment Toolkit, free). Its Show-ADTInstallationWelcome -CloseProcesses command shows a prompt before closing apps. Check the PSADT documentation for your version, because commands changed between v3 and v4. Also set deployment deadlines outside working hours, so most apps are already closed.

If you still get 1603, open the MSI log C:\Windows\Temp\chrome-install.log on the PC and search for Return value 3. The lines just above it show the real reason.

✓ Check it worked
  • On a test PC, open Software Center (or wait for the deadline). AppEnforce.log shows Process … terminated with exitcode: 0.
  • Check the installed version on the PC:
PowerShell · confirm installed version
(Get-Item "C:\Program Files\Google\Chrome\Application\chrome.exe").VersionInfo.ProductVersion

In the deployment status, that PC moves from Error to Success. After the fix is deployed widely, the 1603 group on the Error tab shrinks.

FIX FMECM says success, but the scanner still flags the app (per-user installs)

Chrome, Zoom and Teams can install inside each user's profile (C:\Users\name\AppData). MECM installs machine-wide, so the old per-user copy stays behind and keeps getting flagged.

Step 1: find the per-user copies (Run Scripts)
  1. Go to Software Library → Scripts → Create Script. Name it Find per-user apps and paste the script below. Finish.
  2. A second admin approves it: right-click → Approve/Deny. If you're the only admin, you can allow self-approval: Administration → Site Configuration → Sites → Hierarchy Settings → General, untick Script authors require additional script approver.
  3. Right-click a collection → Run Script → choose the script.
  4. See the results in Monitoring → Script Status → select the run → Show Status. The output column shows what each PC returned.
PowerShell · Run Script: list per-user installs
$paths = @(
  'AppData\Local\Google\Chrome\Application\chrome.exe',
  'AppData\Roaming\Zoom\bin\Zoom.exe',
  'AppData\Local\Microsoft\Teams\current\Teams.exe'
)
$found = foreach ($u in Get-ChildItem C:\Users -Directory) {
  foreach ($p in $paths) {
    $f = Join-Path $u.FullName $p
    if (Test-Path $f) { "$($u.Name): $(Split-Path $p -Leaf) $((Get-Item $f).VersionInfo.ProductVersion)" }
  }
}
if ($found) { $found -join '; ' } else { 'None' }
Step 2: remove them (runs as each user)

A per-user install must be removed while that user is logged on, because it lives in their profile. Create an MECM Application with the script below, and on the User Experience tab set Installation behavior = Install for user. Deploy it as Required to a user collection, such as All Users.

PowerShell · remove per-user Chrome (runs as the user)
$setup = Get-ChildItem "$env:LOCALAPPDATA\Google\Chrome\Application\*\Installer\setup.exe" -ErrorAction SilentlyContinue |
         Select-Object -First 1
if ($setup) {
  Get-Process chrome -ErrorAction SilentlyContinue | Stop-Process -Force
  Start-Process $setup.FullName -ArgumentList '--uninstall --force-uninstall' -Wait
}
exit 0

For Zoom, the vendor provides its own clean-up tool (CleanZoom). For other apps, check the vendor's documentation for the per-user uninstall command. To stop users installing into their profile again, block it with AppLocker rules for %LOCALAPPDATA%.

✓ Check it worked

Run the Find per-user apps script again on the same collection. The PCs you fixed now return None. On the next vulnerability scan, the findings for those apps disappear from those PCs.

FIX G0x87D00324 App installed, but MECM can't detect it

The install worked, but the application's detection method looks for the wrong thing, so MECM reports a failure (or keeps reinstalling).

Do this
  1. On a PC where the new version is installed, find the real version number: right-click the program's .exe → Properties → Details → File version. Or use the version command from Fix E.
  2. In MECM, open the application → Deployment Types tab → the deployment type → Properties → Detection Method → Add Clause (or edit the existing one).
  3. Set:
    Setting TypeFile System
    TypeFile
    Path%ProgramFiles%\Google\Chrome\Application
    File or folder namechrome.exe
    32-bit app on 64-bit systemsUntick (Chrome installs to 64-bit Program Files)
    RuleThe file system setting must satisfy the following rule
    Property / Operator / ValueVersion · Greater than or equal to · <new version>
  4. For MSI apps that keep the same product code for each version, you can use Windows Installer as the setting type, with the product code. Use the file version if the product code changes with every release.
✓ Check it worked

On the test PC, run Control Panel → Configuration Manager → Actions → Application Deployment Evaluation Cycle → Run Now. In AppDiscovery.log, the app now shows +++ Discovered application instead of +++ Application not discovered. Its deployment status changes to Success.

FIX HOld version stays installed next to the new one

Supersedence uninstalls the old version using the old application's uninstall program. If that command is wrong or missing, the old version stays and keeps getting flagged. Java is the classic example.

Step 1: find the real uninstall command

Run on a PC that has the old version:

PowerShell · list installed versions and their uninstall codes
$keys = 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*',
        'HKLM:\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\*'
Get-ItemProperty $keys -ErrorAction SilentlyContinue |
  Where-Object DisplayName -like '*Java*' |
  Select-Object DisplayName, DisplayVersion, PSChildName, UninstallString

For MSI installs, PSChildName is the product code, like {26A24AE4-…}. The uninstall command is msiexec /x {PRODUCT-CODE} /qn /norestart. Put this in the old application's Deployment Type → Programs → Uninstall program.

Step 2: clean up existing PCs in one go (Run Scripts)
PowerShell · Run Script: remove Java 8 builds older than a version
$keep = [version]'8.0.4310'   # set to your approved build (DisplayVersion format)
$keys = 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*',
        'HKLM:\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\*'
$old = Get-ItemProperty $keys -ErrorAction SilentlyContinue | Where-Object {
  $_.DisplayName -like 'Java 8 Update*' -and $_.PSChildName -like '{*}' -and [version]$_.DisplayVersion -lt $keep
}
if (-not $old) { 'Nothing to remove'; exit 0 }
foreach ($a in $old) {
  $p = Start-Process msiexec.exe -ArgumentList "/x $($a.PSChildName) /qn /norestart" -Wait -PassThru
  "$($a.DisplayName) $($a.DisplayVersion): exit $($p.ExitCode)"
}

Run the list command first to see the DisplayVersion format on your PCs, then set $keep. Test on the pilot collection first.

✓ Check it worked

In Monitoring → Script Status, each PC shows exit 0 per removed version (3010 means removed, restart needed). Run the list command again on a PC: only the approved version remains.

FIX I0x87D00607 Content not found

Do this
  1. Go to Monitoring → Distribution Status → Content Status → find the application. Every distribution point should be green.
  2. If one isn't, right-click the application in Software Library → Distribute Content → add the missing distribution points or groups. If it shows an error, use Redistribute.
  3. If content is green everywhere, the PC's network isn't in a boundary group linked to a DP. Fix that as in Fix D, step 3.
✓ Check it worked

Retry the install on a failed PC. Its CAS.log and ContentTransferManager.log show the download completing, then AppEnforce.log shows the install running.

FIX J3010 Restart required

This is not a failure. The install worked and the PC needs a restart to finish.

Do this
  1. Go to Administration → Client Settings → [your settings] → Computer Restart. Set Configuration Manager can force a device to restart = Yes, with a countdown such as 90 minutes and a reminder before it.
  2. In the application's deployment type, on the User Experience tab, set the post-installation behavior to Determine behavior based on return codes.
✓ Check it worked

After the restart, the deployment status changes from "Pending restart" to Success.

FIX KWindows updates fail (0x8024xxxx and similar)

Step 1: check the basics (Run Scripts)
PowerShell · Run Script: pending restart and free disk
$cbs = Test-Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Component Based Servicing\RebootPending'
$wu  = Test-Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update\RebootRequired'
$free = [math]::Round((Get-PSDrive C).Free / 1GB, 1)
"PendingRestart=$($cbs -or $wu); FreeGB=$free"

If PendingRestart is True, restart the PC first. If FreeGB is below 10, free up disk space; Disk Cleanup and old user profiles are the usual targets. Many update failures disappear after just these two steps.

Step 2: repair the Windows Update components (on one PC, as admin)
cmd · reset Windows Update and repair system files
net stop wuauserv
net stop bits
net stop cryptsvc
ren C:\Windows\SoftwareDistribution SoftwareDistribution.old
ren C:\Windows\System32\catroot2 catroot2.old
net start cryptsvc
net start bits
net start wuauserv
DISM /Online /Cleanup-Image /RestoreHealth
sfc /scannow

DISM and sfc can take 15–30 minutes. Run Scripts is meant for short scripts, so for many PCs, deploy these commands as an MECM Package/Program, or as a task sequence, instead.

✓ Check it worked

On the PC, run Control Panel → Configuration Manager → Actions → Software Updates Scan Cycle, then Software Updates Deployment Evaluation Cycle.

  • WUAHandler.log shows a successful scan with no error codes.
  • UpdatesDeployment.log shows the updates installing.
  • Run Get-HotFix | Sort-Object InstalledOn -Descending | Select-Object -First 5 and confirm the newest updates appear.
  • In the console, the PC is now counted as Compliant on the update deployment.

06Weekly routine and targets

Track three numbers every week. If they improve, the fixes are working.

≥ 95%of PCs with Client Activity = Active
Monitoring → Client Status → Client Activity
≥ 95%success on each deployment
Monitoring → Deployments → Compliance %
Fallingfinding count in your vulnerability scanner, week on week
  1. Monday · 30 minNote the member count of Clients - Inactive. Run the triage script from section 02 and work through Fixes A–D.
  2. Tuesday · 1 hourOpen the Error tab on each active deployment. Fix the top 2–3 error codes with Fixes E–K, test on one PC, then roll out.
  3. Friday · 15 minWrite the three numbers above in a spreadsheet. Anything that has failed twice gets reimaged, or logged as an exception with an owner and a review date.
