## 1. Executive summary

**What this is:** A .NET **MAUI Android** app (`GpsSync`, product name **HitachiDispatch**) for
field-engineer dispatch + live GPS tracking. It is a mobile client only — there is **no custom
backend in this repo**. All server-side work (auth, database, REST API) is delegated to **Supabase
(cloud)**, which is itself **PostgreSQL + GoTrue (auth) + PostgREST (REST) + Realtime**.

**The migration goal (as stated):** move off Supabase cloud so the system is
1. runnable on **localhost** first, then
2. backed by **SQL Server**, and
3. eventually deployed to **another cloud**.

**The core tension you need to know up front:** The app talks to Supabase through the official
`Supabase` C# SDK (`supabase.Auth.SignIn`, `supabase.From<T>()`). That SDK speaks two Supabase-only
HTTP protocols — **GoTrue** for auth and **PostgREST** for data. **A plain PostgreSQL or SQL Server
database does not expose those endpoints.** So "point the app at SQL Server" is **not** a
connection-string change — it requires either (a) running the Supabase API layer in front of the DB,
or (b) replacing the backend with your own API. See §7.

**Why login/create-user fails on localhost right now:** almost certainly a combination of
(1) Android can't reach `localhost`/`127.0.0.1` — that address means the *phone/emulator itself*, not
your PC; (2) Android blocks cleartext **HTTP** by default and local Supabase is HTTP; and/or
(3) you may be pointing at a bare DB with no Supabase API layer, so the auth endpoints don't exist.
Full analysis in §8.

> ⚠️ **Repo won't compile as-is:** `MauiProgram.cs` references `AppConfig.SupabaseUrl` and
> `AppConfig.SupabaseKey`, but **there is no `AppConfig.cs` in the repo** (and no `.gitignore`).
> This looks like decompiled/re-uploaded source; the config file that holds the backend URL was not
> included. Whatever URL you set there is the single most important input to the network problem.

## 3. How the app talks to the backend

Single Supabase client, registered as a singleton in `MauiProgram.cs:79`:

```csharp
new Client(AppConfig.SupabaseUrl, AppConfig.SupabaseKey,
           new SupabaseOptions { AutoConnectRealtime = false });
```

- **Auth** → `supabase.Auth.*` (GoTrue): `SignIn`, `SignUp`, `SetSession`, `RefreshSession`,
  `SignOut`, `Update`. Tokens cached in `SecureStorage` (`sb.access_token`, `sb.refresh_token`).
  Token auto-refresh every 45 min (`SupabaseTokenRefreshService.cs`).
- **Data** → `supabase.From<T>()` (PostgREST): reads/writes/filters on 3 tables.
- **No RPCs**, **no Storage**, **Realtime off**.
- The backend URL is **hard-coded via `AppConfig`** — it is **not** runtime-configurable from the
  Settings screen. (Worth changing during migration; see §9.)

| `DispatchJobRecord.cs` | `dispatch_jobs` | `id` (PK), `engineer_user_id`, `admin_user_id`, `title`, `description`, `status`, `created_at`, `completed_at` |

## 7. The migration challenge: Supabase / Postgres → SQL Server

**Supabase is not just a database.** The C# SDK depends on Supabase's HTTP API surface:

- `Auth.*` → **GoTrue** service (`/auth/v1/...`)
- `From<T>()` → **PostgREST** service (`/rest/v1/...`)

Neither PostgreSQL nor SQL Server serves those endpoints on their own. Therefore there are two
realistic migration strategies, and they diverge a lot:

### Path A — Stay on the Supabase stack, self-hosted (fastest to "localhost", keeps code)
- Run **self-hosted Supabase locally** (Docker / Supabase CLI). This keeps GoTrue + PostgREST +
  **PostgreSQL**, so the app needs **only a config change** (`AppConfig` URL/key) plus the Android
  cleartext/host-IP fixes in §8.
- **Trade-off:** the database stays **PostgreSQL**, not SQL Server. This does *not* satisfy the
  "SQL Server" requirement, but it's the quickest way to be running locally today and to unblock the
  login issue. Good as an interim step. Later cloud deploy = host the Supabase stack on your cloud.

### Path B — Replace the backend with your own API on SQL Server (satisfies "SQL Server", larger effort)
- Build an **ASP.NET Core Web API** backed by **SQL Server** (EF Core), with auth via **ASP.NET Core
  Identity + JWT** (to replace GoTrue), and controllers to replace the 3 PostgREST tables + the
  email-confirmation, password-reset, and single-device-token flows.
- Then in the app, **replace the Supabase SDK** with `HttpClient`/Refit calls to the new API
  (swap out `Auth.*` and `From<T>()` usages across ~15 files — see the usage list in §3).
- Reproduce what Supabase gave for free: RLS → server-side authorization, email confirmation +
  password-reset emails, JWT refresh, deep-link callbacks.
- **Trade-off:** real effort, but it's the only path that ends on SQL Server and a portable cloud.

> **Decision (2026-09-15): SQL Server is required → Path B.** Since the end state must be SQL Server
> and no local backend exists yet (see §7a), Path A (self-hosted Supabase) would only be throwaway
> Postgres work. We go straight to Path B. Note this means **login cannot work locally until the new
> backend's first auth endpoints exist** — there is no config-only fix.
>
> _(Path A remains a possible **optional** interim only if you want to prove the existing app
> binary works end-to-end while the new backend is built — but it keeps Postgres and is discardable.)_

## 8. Root-cause analysis: "network related issues" on login / create user

The error text you see ("Connection failed. Check your internet and try again.") is produced by
`ToFriendlyError()` in `LoginViewModel.cs:175` / `RegisterViewModel.cs:100` whenever the exception
message contains "network", "unable to connect", or "timeout". So the app is genuinely failing to
reach the backend. Ranked most-likely causes:

1. **Android `localhost` ≠ your PC.** On an emulator/device, `http://localhost` or `127.0.0.1`
   points at the *phone itself*. If `AppConfig.SupabaseUrl` is `localhost`/`127.0.0.1`, every auth
   call fails.
   - **Android emulator:** use **`http://10.0.2.2:<port>`** (special alias to the host loopback).
   - **Physical device / Genymotion:** use your PC's **LAN IP** (e.g. `http://192.168.x.x:<port>`),
     device and PC on the same network, firewall open for the port.

2. **Cleartext HTTP is blocked.** Self-hosted/local Supabase serves plain **HTTP**, but the app
   targets a modern Android API where cleartext is disabled by default, and `AndroidManifest.xml`
   has **no** `android:usesCleartextTraffic="true"` and **no** network-security-config. Result:
   the HTTP request is refused before it leaves the app → looks like a network error.
   - Fix: add a network-security config permitting cleartext to your dev host (preferred, scoped),
     or `android:usesCleartextTraffic="true"` on `<application>` for dev builds.

3. **Pointing at a bare DB with no Supabase API layer.** If "run at localhost" currently means a
   local **Postgres or SQL Server** *without* the Supabase services, then `SignIn`/`SignUp` hit
   `/auth/v1/...` which doesn't exist → connection refused / 404 → network-style failure. The SDK
   needs GoTrue + PostgREST running (i.e. the full self-hosted Supabase stack), not just a DB.

4. **Service not running / wrong port / wrong key.** Local Supabase (CLI) default API port is
   `54321`; a Docker `docker-compose` self-host fronts everything through **Kong** on `8000`.
   The `anon`/`service` key must match that specific local instance, not the cloud project's key.

5. **Missing `AppConfig.cs`** (see §6) — if it's absent or malformed, the URL may be empty/wrong.

**Fastest way to confirm the real cause:** open the in-app **Network Log** page (there's a
`NetworkMonitorService` + `NetworkLogPage`), or read the OS logs, and check the exact exception.
Also do a `Set-Session`-free smoke test: from the emulator's browser, open
`http://10.0.2.2:<port>/auth/v1/health` — if that fails, it's networking/cleartext (causes 1–2); if
it 404s, the Supabase API layer isn't there (cause 3).
