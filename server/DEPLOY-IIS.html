Deploy HitachiDispatch to Windows Server + IIS

GpsSync API · SQL Server (local) · HTTPS over Tailscale

Target server: Windows Server  •  IIS  •  SQL Server  •  SSMS  •  Tailscale

Is it ready to deploy as-is?  Almost — no code changes, but the repo is packaged for Docker/Linux. For IIS you install the .NET 10 Hosting Bundle, repoint the connection string at your local SQL Server, set a real JWT key, publish, and let Tailscale provide HTTPS (it replaces Caddy). The app auto-creates the database, runs migrations, and seeds the admin on first start, so there is no manual schema step.

⚡ Fast path — the repo ships copy-paste artifacts

Three companion files automate most of this guide. The prerequisites still apply first: install IIS → the .NET 10 Hosting Bundle → Tailscale (Step 0).

The whole deployment, in an elevated PowerShell on the server:

# 1. publish + configure IIS in one shot
cd C:\path\to\geo\server\deploy
.\deploy-iis.ps1

# 2. paste the two lines the script prints into SSMS (lets the app reach SQL)
#    CREATE LOGIN [IIS AppPool\GpsSyncApi] FROM WINDOWS;
#    ALTER SERVER ROLE dbcreator ADD MEMBER [IIS AppPool\GpsSyncApi];

# 3. first run — creates the GpsSync DB + tables, seeds the admin
curl http://localhost:5080/health

# 4. run gpssync-maintenance.sql once in SSMS (indexes + retention)

# 5. expose over HTTPS to the phones (public, no per-phone setup)
tailscale funnel --bg http://localhost:5080

Handy switches: -JwtKey "<secret>" to set your own key · -ConnectionString "<sql-auth string>" to use a SQL login instead of Windows auth · -Port 8080 to change the internal port. Re-running preserves the existing JWT key, so redeploys don’t log everyone out.

Want to understand each piece first? The manual walkthrough below does exactly the same thing by hand.

Architecture

Only Tailscale faces the outside. IIS and SQL Server stay on localhost, exactly like the Docker design where only Caddy was exposed.

Flow: phone → Tailscale (HTTPS, valid cert) → IIS on localhost:5080 (HTTP) → SQL Server on localhost:1433.

0 · Install prerequisites on the server

ComponentStatusAction
IIS (Web Server role)you have itEnsure the Web Server (IIS) role is installed before the Hosting Bundle.

SQL Serveryou have itEnable mixed-mode auth if you'll use a SQL login (Step 1).
SSMSyou have itUsed in Step 1.

Download the Hosting Bundle from Microsoft (search “ASP.NET Core 10.0 Windows Hosting Bundle”, on dotnet.microsoft.com/download/dotnet/10.0). After installing it, restart IIS so the module loads:

net stop was /y
net start w3svc
Order matters. If you install the Hosting Bundle before IIS, re-run the bundle (Repair) afterward — otherwise the ASP.NET Core Module won’t be registered and every request returns HTTP 500.19 / 500.21.

1 · Prepare SQL Server (SSMS)

The API creates the GpsSync database itself on first run — you only need to give it a login that’s allowed to do so. Pick one option.

Option A — Windows auth via the app-pool identity recommended, no password in config

Do this after Step 4 creates the app pool. In SSMS:

-- Let the IIS app pool sign in to SQL, and create/own its database
CREATE LOGIN [IIS APPPOOL\GpsSyncApi] FROM WINDOWS;
ALTER SERVER ROLE dbcreator ADD MEMBER [IIS APPPOOL\GpsSyncApi];
-- (After the first successful run you may drop dbcreator and instead grant
--  db_owner on the GpsSync database only, for least privilege.)

Option B — Dedicated SQL login (matches the existing connection-string format)

CREATE LOGIN gpssync WITH PASSWORD = 'Strong-Passw0rd!';
ALTER SERVER ROLE dbcreator ADD MEMBER gpssync;

For Option B, SQL Server must allow SQL logins: right-click the server → Properties → Security → “SQL Server and Windows Authentication mode”, then restart the SQL Server service.

Prefer least privilege from day one? Pre-create an empty DB in SSMS (CREATE DATABASE GpsSync;), then grant your login db_owner on it and skip dbcreator. Migrations will just build the tables.

2 · Publish the API

On your dev machine (or on the server if the SDK is installed), from the repo:

# from server\GpsSync.Api
dotnet publish -c Release -o C:\publish\GpsSyncApi

This produces the DLLs plus a generated web.config (the ASP.NET Core Module handler, in-process hosting). Copy the whole C:\publish\GpsSyncApi folder to the server, e.g. to C:\inetpub\GpsSyncApi.

Framework-dependent publish needs the .NET 10 runtime on the server — the Hosting Bundle from Step 0 provides it, so nothing extra to install.

⚡ server/deploy/deploy-iis.ps1 does this step and Steps 3–4 for you. Run it in an elevated PowerShell; the manual instructions below are for understanding or a hand deploy.

3 · Set the connection string + JWT key

Edit C:\inetpub\GpsSyncApi\appsettings.json on the server (or create appsettings.Production.json beside it). Three edits:

⚡ The repo already includes server/GpsSync.Api/appsettings.Production.json with the Windows-auth connection string, and deploy-iis.ps1 fills its Jwt:Key automatically. Read on only if you’re configuring by hand or switching to a SQL login.

a. Connection string → your local SQL Server

// Windows auth (Option A):
"ConnectionStrings": {
  "Default": "Server=localhost;Database=GpsSync;Trusted_Connection=True;TrustServerCertificate=True;Encrypt=False"
}

// OR SQL login (Option B):
"ConnectionStrings": {
  "Default": "Server=localhost;Database=GpsSync;User Id=gpssync;Password=Strong-Passw0rd!;TrustServerCertificate=True;Encrypt=False"
}

If SQL Server is a named instance, use Server=localhost\SQLEXPRESS (or your instance name).

b. Generate + set a real JWT key

In PowerShell:

[Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))

Paste the result into Jwt:Key (replace the __SET_VIA_ENV__… placeholder). Keep the same key across restarts, or every issued token is invalidated.

c. Remove the Urls line

Delete "Urls": "http://0.0.0.0:5080" — under IIS in-process hosting the site binding controls the port, and leaving it just logs a warning. (IIS will serve it on whatever port you bind in Step 4.)

Secrets note. Putting the DB password / JWT key in appsettings.json is fine for a solo internal deploy. To keep them out of the file, set them as environment variables in web.config under <aspNetCore><environmentVariables> instead (ConnectionStrings__Default, Jwt__Key).

4 · Create the IIS site

1
Application Pools → Add Application Pool. Name it GpsSyncApi, .NET CLR version = “No Managed Code”, Managed pipeline = Integrated.

“No Managed Code” is correct — ASP.NET Core does not use IIS’s CLR; the ASP.NET Core Module loads .NET 10 itself.

2
Sites → Add Website. Site name GpsSyncApi; physical path C:\inetpub\GpsSyncApi; app pool GpsSyncApi; binding http, port 5080, host name blank. (HTTP is fine here — Tailscale adds HTTPS in front.)
3
If you chose Windows auth (Option A), now go back to Step 1 and run that SQL — the login IIS APPPOOL\GpsSyncApi only exists once the app pool does.

5 · First run + verify

On the server, hit the health endpoint (the first request boots the app, which runs migrations and seeds the admin):

curl http://localhost:5080/health
# -> {"status":"ok"}
  • In SSMS, refresh Databases — GpsSync now exists with profiles, dispatch_jobs, gps_pings, Identity + token tables.
  • Seeded admin for first login: admin@local.test / Admin!23 (change it — see Hardening).
If you get HTTP 500: it’s almost always the DB connection (wrong server/instance, login can’t create the DB) or a bad config value. See Troubleshooting to turn on the stdout log.

6 · Put HTTPS in front with Tailscale

Install Tailscale, sign in, then find this machine’s name:

tailscale up
tailscale status      # note the name, e.g. winserver.tailnet-abc.ts.net

Choose how the phones reach it

 Serve — tailnet onlyFunnel — public internet
Who can reach itOnly devices on your tailnetAnyone on the internet (via the .ts.net URL)
Phone setupEach phone must install Tailscale + join the tailnetNothing on the phone — just the app
Best forA small pilot / your own test phones200 field engineers on mobile data
# Private (tailnet-only):
tailscale serve --bg http://localhost:5080

# Public (field engineers, no per-phone setup):
tailscale funnel --bg http://localhost:5080

# Check what's configured:
tailscale serve status
Verify the exact syntax with tailscale serve --help / tailscale funnel --help — this CLI has changed across versions. For Funnel you must also: enable HTTPS certificates + MagicDNS in the Tailscale admin console, and give this machine the funnel node attribute in your ACLs. Funnel only allows ports 443 / 8443 / 10000 and is aimed at modest traffic — fine to launch on; if 200 engineers hammer it, move to a real domain + cert later.

Test from a phone browser (on mobile data if using Funnel):

https://winserver.tailnet-abc.ts.net/health   # -> {"status":"ok"} with a valid padlock

7 · Point the mobile app at the server

In AppConfig.cs (repo root), set the Release URL to your Tailscale address:

// #else  (Release / the APK you hand to engineers)
public const string ApiBaseUrl = "https://winserver.tailnet-abc.ts.net";
  • It’s real HTTPS with a valid cert, so you need no Android cleartext exception for the cloud address.
  • Build the app in Release for Android → distribute the .apk. Engineers install, open, log in.
  • Using Serve (not Funnel)? Each phone must be signed into Tailscale first.

8 · Keep it running (better than dotnet run)

  • IIS auto-starts the site on boot and restarts the worker if it crashes — this is why IIS beats a foreground process.
  • App pool → Advanced Settings: set Start Mode = AlwaysRunning and Idle Time-out (minutes) = 0 so the API never cold-stops.
  • Tailscale runs as a service; --bg serve/funnel config is restored automatically after a reboot.
  • Confirm both survive a reboot: restart the server, then hit the /health URL from your phone.

9 · Before real traffic — hardening checklist

⚡ The index and GPS retention items below are done for you by server/deploy/gpssync-maintenance.sql — run it once in SSMS against the GpsSync database.
  • Change the seeded admin (admin@local.test / Admin!23) — log in and reset, or edit SeedData.cs and redeploy.
  • SQL Server backups — a SQL Agent job / Maintenance Plan for the GpsSync DB, copied off the server.
  • GPS retention job — delete gps_pings older than 30–90 days (≈1.15M rows/day at 200 engineers). Keeps the DB small and fast.
  • Index — add (UserId, CreatedAt DESC) on gps_pings for the map/latest queries.
  • Rotate the JWT key + SQL password if they were ever shared.
  • Real email for password resets — set Email:Mode=Smtp + SMTP settings (otherwise reset codes go to the log).

Troubleshooting

SymptomLikely cause / fix
500.19 / 500.21, or “Handler … has a bad module”Hosting Bundle not installed, or installed before IIS. Install/repair it, then net stop was /y && net start w3svc.
Site returns HTTP 500 on every requestApp failed to start — usually DB. Turn on the log (below), read logs\stdout, or check Event Viewer → Windows Logs → Application.
DB / login errorsWrong Server= (named instance?), login lacks dbcreator, or mixed-mode auth off for a SQL login.
Phone can’t reach itFunnel not enabled in admin console / missing node attribute; or you used Serve and the phone isn’t on the tailnet. Test /health in the phone browser.
Cert warning on the appYou pointed the app at http://… or a raw IP. Use the https://…ts.net name Tailscale issued.

Enable the startup log temporarily — in web.config, on the <aspNetCore> element set stdoutLogEnabled="true" and stdoutLogFile=".\logs\stdout", create a logs folder, retry, then read the newest file. Turn it back off afterwards.

Host this guide itself via Tailscale

This page is a single self-contained HTML file (server\DEPLOY-IIS.html). To open it from any device on your tailnet, drop it in a folder and serve that folder on a spare HTTPS port (keep 443 for the API):

# serve the folder containing this file on https port 8443 (tailnet-only)
tailscale serve --bg --https=8443 C:\path\to\guide-folder

# then open, from any tailnet device:
https://winserver.tailnet-abc.ts.net:8443/DEPLOY-IIS.html

Or simplest of all: just double-click the file to open it in the server’s browser. Confirm the exact serve flags with tailscale serve --help.
